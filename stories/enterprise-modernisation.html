03 / ENTERPRISE MODERNISATION

Modern software doesn't always start from zero.

Some of the best engineering happens inside applications that already carry years of history, thousands of real users, and a release schedule that won't pause for a refactor.

  • LEGACY MIGRATION
  • SWIFT
  • SWIFTUI
  • CONCURRENCY
  • MODULARISATION
  • SPM

The problem

A full rewrite is always tempting and almost always the wrong call. You trade a working system with known flaws for an unfinished one with unknown flaws, and delivery freezes for however long it takes. Which is reliably longer than anyone estimated.

How the migration proceeds

  1. 01

    DRAW BOUNDARY

    Pick one module and define its public surface precisely. Nothing else in the codebase is allowed to reach past it.

  2. 02

    MIGRATE BEHIND IT

    Rewrite the internals freely. Behaviour at the boundary stays identical, which is what makes the change invisible.

  3. 03

    SHIP

    Release with the boundary in place. The work goes out in the ordinary cadence rather than waiting for a big cutover.

  4. 04

    REPEAT

    The dependency graph is now smaller and better understood, so the next boundary is easier to draw than the last.

The approach

Incremental migration works better. Draw a boundary, move one module across it, ship, repeat. New work lands in modern Swift and SwiftUI. Older layers get modernised as they're touched, not on some separate track that never gets prioritised.

Structured concurrency goes in where it removes real bugs, not everywhere at once. Package boundaries make the dependency graph visible, so each migration is smaller than the last. The codebase gets easier to change while the work is happening.

Nobody downstream should be able to tell a migration is underway. That's the bar.

The part that took the longest

Sequencing. Choosing which boundary to draw first determines whether the second migration is easier or harder than the first.

What the work involved

  • The constraint

    Real users and a release schedule that won't pause for a refactor.

  • The engineering

    Module boundaries, incremental Swift and SwiftUI migration, structured concurrency.

  • The ownership

    Migration strategy, review standards and the sequencing of the work.

  • The outcome

    A codebase that gets easier to change while it keeps shipping.
